# v2.6.1 deep dive

## Summary

v2.6.1 is a patch release containing exactly three fixes, all found by the full security audit of the released v2.6.0 tree (39 candidates run through adversarial verification → 24 confirmed findings; the approved fix scope was the one HIGH finding plus the host-killer group F-06/F-07). There are no new features and no breaking changes: the public-contract impact is additive only (one new refusal reason, one rejection kind that previously existed only as dead code, and optional diagnostic fields). Suite: 305 tests (303 pass, 0 fail, 2 pre-existing RSA-PSS skips), up from 298 in v2.6.0, with 7 new regression tests. All other audit findings are untouched and queued.

## 1. F-01 - idempotency replay across subjects (HIGH)

### The hole in 2.6.0

Both ledgers accept an `idempotencyKey` so a host can safely retry a reservation: a second call with the same key returns the original reservation as `duplicate: true` instead of reserving twice. In v2.6.0 the duplicate branch keyed ONLY on the idempotency key - it never checked WHO was asking or WHAT they were asking for. Any caller who learned or guessed another subject's key could replay it with arbitrary record ids (disclosure ledger) or a different subject/action/cost (action budget) and receive `allowed: true, duplicate: true` against the original subject's reservation: the stranger's extraction was charged to the victim's reservation, and the cohort ceiling the reservation was holding could be ridden past. Audit harness verdict before the fix: `replayAllowed: true, duplicate: true, sameReservation: true`, and the post-commit union contained the stranger's 4 ids.

### The fix

A replay now has to match the reservation the key first created, checked at the last trust decision point: the duplicate branch of reserve, inside the same store transaction, so the check cannot be raced.

- **Disclosure ledger** (`src/tier2-active/disclosure-ledger.ts`): each reservation now stores an `idemFingerprint` - a 64-bit FNV-1a hash over subject + long-flag + count-only amount + the sorted record ids. The duplicate branch returns the duplicate only when the stored subject AND the stored fingerprint both match the incoming request.
- **Action budget** (`src/tier2-active/action-budget.ts`): the reservation already stores subject/action/cost/cohortId, so the duplicate branch compares those four fields directly (`samePayload`); no new stored state was needed.
- Any mismatch is refused with the new reason `idempotency_conflict` (the reason union was extended in both modules). The doc comments on `idempotencyKey` in both modules and `docs/LIMITATIONS.md` now state the contract explicitly: keys MUST be host-generated and unguessable - and a guessed key can no longer ride on another subject's reservation.

### Compatibility note

A reservation persisted by v2.6.0-or-earlier code carries no fingerprint. Rather than honoring it unverified (the old, exploitable behavior), a replay against it now fails closed with `idempotency_conflict` for the rest of that reservation's TTL - 2 minutes by default, 15 minutes maximum on the long-reservation path. Fresh reservations are unaffected, and an exact replay (same subject, same payload) still returns `duplicate: true`.

## 2. F-06 - store failures fail closed instead of throwing

### The hole in 2.6.0

The ledgers persist state through a host-provided store. In v2.6.0, a corrupt or failing store threw raw exceptions out of the SDK's public methods: a truncated JSON state threw `SyntaxError: Unterminated string in JSON`, a wrong-shaped state threw `TypeError: Cannot convert undefined or null to object`, and CAS exhaustion threw a plain `Error`. The audit's live test with a naive host wiring (no try/catch around the SDK, the way the README's minimal examples wire it) showed the consequence plainly: with a dead store, the host process DIED on its first request (unhandled rejection). A storage problem in an anti-abuse layer must never become an availability problem for the host.

### The fix

Store corruption and failure are converted to structured refusals at each module's boundary, so no store exception can escape into host request handling:

- **Disclosure ledger:** new `LedgerStoreError` type; stored state is parsed AND shape-validated on read (`parseStoredState`, `isValidLedgerState` - core fields, bucket numerics, evidence and idempotency shapes, the registry, and every stored bitmap must decode). A mutation aborts without writing when the transaction updater sees an invalid shape, and CAS exhaustion throws `LedgerStoreError` internally, which every public method converts: `reserveDisclosure` refuses with reason `store_conflict` (the reason existed in the v2.6.0 type union but was dead code - never returned), `commitReservation` returns `{committed: false, reason: "store_conflict"}`, release/sweep/recordEvidence/declareRegistry return a result carrying `reason: "store_conflict"`, and `snapshot` / `checkRegistryCompleteness` return an empty-state fallback snapshot plus a `storeError: "store_conflict"` field.
- **Action budget:** new `StoreDataError` beside the existing (never-thrown) `StoreConflictError`; `isValidActionBudgetState` + `parseActionBudgetState` validate on read; the mutate path wraps transaction throws and audit-path put throws and aborts on invalid shape; commit/release/sweep/declare/pacing/clear/snapshot all return `store_conflict` refusals through the `isStoreFailure` helper.
- **Quota guard** (`src/tier2-active/quota-guard.ts`): new rejection kind `store_unavailable`. The peek loop validates the returned snapshot (an object with a finite numeric `count`) and catches store throws, and the record loop catches too - `checkRequest` now answers a structured 429 decision instead of propagating the store's exception.

### Live retest

Re-run against the audit's own harnesses and live hosts on the patched build: truncated JSON and wrong-shape JSON both return `{"allowed": false, "reason": "store_conflict"}` instead of throwing. The naive-wiring live host with a dead store answered two requests with HTTP 429 and the process stayed alive (before: died at the first request). A correctly wired protected host under forced store failure went from HTTP 500 (it had survived only via its own try/catch) to a structured HTTP 429 `store_unavailable` ("Quota store unavailable; the request was rejected rather than admitted unaccounted."). On a healthy store, legit requests answered 200 ×3 at ~1-8 ms - no regression. The failure mode is deliberately fail-CLOSED for admission decisions: a request the SDK cannot account for is rejected, never admitted unaccounted.

## 3. F-07 - sparse chunked bitmap for the record union

### The hole in 2.6.0

The disclosure ledger tracks the exact union of served record ids as a dense bitmap: one bit per id, sized by the largest id seen. Memory and serialization therefore grew with the largest id VALUE, not with the number of records. A dataset with snowflake-scale or int64 ids - no attacker required - hit this in normal operation: reserving a single record with id 10^8 took 1,439 ms and produced 16,670,239 bytes of serialized state; reserving id 2^53-1 threw `RangeError: Array buffer allocation failed` straight out of `reserveDisclosure`.

### The fix

The dense bitmap is replaced by a **sparse chunked bitmap** in `disclosure-ledger.ts`: a `Map<chunkIndex, Uint8Array(1024)>` over 8192-bit chunks. State and work now grow with the NUMBER of distinct records, never with id values. The wire format is `"s1." + base64url([uint32LE chunkIndex | chunk bytes]*)`. All bitmap helpers (`bitmapFromBase64`, `bitmapToBase64`, `bitmapHas`, `bitmapWithIds`, `bitmapUnion`, `bitmapPopcount`, `bitmapNewIds`) were rewritten on the chunked type. Extreme ids are not refused and none can throw: each costs exactly one 1024-byte chunk, served and metered exactly - which keeps the ledger's exactness contract for precisely the snowflake/int64-id populations that hit this bug.

### Legacy state compatibility

States persisted by v2.6.0-or-earlier code (dense format) still decode: dense bytes are converted to chunks on read, existing persisted ledgers keep working, and the state is rewritten in the sparse `s1.` format on the next write. A hand-built dense state with union byte 0b00001010 (ids {1, 3}) loads with `committedRecords` = 2, re-delivery of those ids is free, and a new id charges exactly once. Malformed sparse payloads raise `LedgerStoreError` and surface as `store_conflict` via the F-06 plumbing, instead of silently decoding to an empty bitmap (which would have quietly zeroed the ceiling's memory).

## 4. Retest numbers

Every number below is from the audit harnesses re-run unmodified against the patched build, plus the package suite:

- **F-01:** stranger replay (ledger) - `replayAllowed: true` → `replayAllowed: false`; post-commit union = the original subject's 4 ids only. Cross-subject/action replay (budget) - `replayAllowed: true, replayCost: 10` → `replayAllowed: false`.
- **F-06:** truncated JSON - thrown `SyntaxError` → `{"allowed": false, "reason": "store_conflict"}`; wrong-shape JSON - thrown `TypeError` → same structured refusal. Naive live host + dead store - process died at first request → two HTTP 429 answers, process alive. Protected live host + forced store failure - HTTP 500 → structured HTTP 429 `store_unavailable`. Healthy store: legit 200 ×3 at ~1-8 ms.
- **F-07:** reserve single id 10^8 - 1,439 ms / 16,670,239 bytes → **3 ms / 1,745 bytes**. Reserve id 2^53-1 - escaped `RangeError` → `allowed: true`, structured reservation, no throw.
- **Suite:** `npm run check` - 298 tests (296 pass) → **305 tests (303 pass, 0 fail, 2 RSA-PSS skips)**, the delta being 7 new regression tests: the replay-refusal matrix on both ledgers, the corrupt/dead-store matrix on both ledgers plus the quota guard, extreme-id cost bounds, and legacy dense-state compatibility. `npm run benchmark:build-sdk` PASS.

## 5. What this patch does not change

- **No behavior change for well-behaved hosts:** prices, budgets, ceilings, pacing, cohort law, calibration defaults and every shipped constant are exactly as in v2.6.0. Hosts with healthy stores and self-generated idempotency keys see no difference except the refusal paths that previously threw or silently succeeded for the wrong subject.
- **The remaining audit findings are NOT fixed here:** F-02, F-03, F-04, F-05, F-08 and the rest of the 24 confirmed findings keep their v2.6.0 behavior (the harness re-run confirms, for example, that unpriced actions are still granted and parallel quota checks still behave as before). They are queued for a later round; this patch deliberately does not touch them.
- **No claim inflation:** the audit's verdict stands as written - none of the three fixes changes any measured-results number in the README, and the known limitations in `docs/LIMITATIONS.md` otherwise stand (the file gains the idempotency-key contract note described above).
