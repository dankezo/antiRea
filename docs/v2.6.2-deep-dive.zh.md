# v2.6.2 深入解析

## 概述

v2.6.2 是一个只有一个主题的补丁版本：时钟纪律（审计项 L-DEEP-2）。对已发布的 v2.6.1 `src/` 代码树的一次全面审计，按每个值的含义对每一次时钟读取进行了分类。有 12 个点通过两个挂钟（`Date.now`）读数相减来计量一个时间间隔 - 一个窗口、一个 TTL、一个衰减年龄、一段补充流逝时间 - 而每一个这样的间隔都会继承挂钟的任何跳变：一次 NTP 校正、一次虚拟机挂起/恢复，或一次手动改时。实验室测试工具在已发布的 2.6.1 模块上实证了两个方向的扭曲：+5 分钟跳变让单个身份在 10 秒真实时间内取走 200 条记录，而窗口预算是 100 条（200%）；-5 分钟跳变让一个已用完的窗口额外多关闭了 300 秒。本补丁把全部 12 个间隔点迁移到单调时钟（`performance.now`，经由一个新的内部模块 `src/internal/mono-clock.ts`），并为两个持久化账本采用混合双截止设计。没有新功能，也没有破坏性变更：对公共契约的影响仅为新增性的（每个被修补的模块多一个可选的 `monoNow` 选项）；现有的 `now` 契约不变，只注入 `now` 的宿主会精确保持修补前的单时钟行为。审计的 CSPRNG 部分没有发现需要修复的问题：`Math.random` 在 `src/` 中出现 0 次。测试套件：322 个测试（320 个通过，0 个失败，2 个原有的 RSA-PSS 跳过），较 v2.6.1 的 305 个有所增加，新增 17 个回归测试，原有测试零修改。

## 1. 挂钟问题

### 时钟跳变如何破坏一个时间间隔

挂钟会跳变。NTP 守护进程以跳变方式校正漂移，虚拟机管理程序会挂起和恢复虚拟机，管理员也会手动设置时间。任何形如 `now - then >= windowMs` 的计算都会悄悄吸收这次跳变：向前跳变让每个已存储的时间戳看起来比实际更老（窗口提前"过期"、TTL 失效、证据衰减），向后跳变则让它们看起来更年轻（窗口超出设计存活、nonce 在 TTL 之后仍"存活"）。不会有任何错误被记录；算术是正确的，错的是输入。对一个反滥用层来说，这正是最糟糕的失效位置，因为它的窗口和预算就是产品本身：在提取者正在行动的那一刻重置预算窗口的跳变，等于一次免费补充；而拉长窗口的跳变，则是对恰好身处其中的合法用户的拒绝服务。

### 实验室证据（已发布的 2.6.1 模块）

审计围绕两个窗口守卫的已发布 2.6.1 `dist` 模块的逐字副本构建了一个实验室测试工具（`l-deep-2-lab/`），两个分支之间唯一的差别是注入的时钟来源：挂钟分支 = 纪元 + 真实流逝 + 一个跳变偏移（模拟跨越 NTP 跳变的 `Date.now`），单调分支 = 永不跳变的来源（模拟 `performance.now`）。配置：60,000 ms 窗口，预算 100 条记录（记录预算）/ 30 次请求（配额守卫），跳变 +/-300,000 ms（5 分钟）。时间为虚拟值，因此重复运行的输出逐字节相同（Node v24.22.1）。

- **场景 1，+5 分钟跳变，记录预算：** 一个身份在 t=0 用完 100/100；10 秒真实时间过去；+300 秒跳变落下；该身份请求一批新的 100 条。挂钟分支：预检把窗口读作已过期，这批被算作一个全新的窗口 - **在 10 秒真实时间内服务了 200 条不同记录 = 窗口预算的 200%**。单调分支：`allowed = false`，这批被计入同一个窗口（`used = 200`，`exceeded = true`）；预算守在每个窗口 100 条。
- **场景 2，-5 分钟跳变，记录预算：** 一个身份用完 100/100；-300 秒跳变落下；在真实第 70 秒读取状态，此时 60 秒窗口本应在第 60 秒已经重置。挂钟分支：`used = 100, remaining = 0` - 窗口要到真实第 **360** 秒才重置，因此封锁比设计**恰好多持续 300 秒**。单调分支：`used = 0, remaining = 100` - 按时重置。
- **场景 3，+5 分钟跳变，配额守卫滑动窗口：** t=0 时 30 次请求（匿名层级的上限）；跳变落下；1 秒真实时间后第二波 30 次请求到达；守卫的决策输入是 `peek().count`。挂钟分支：`count = 30` - 第一波被当作"超过 60 秒"修剪掉了，窗口把它们忘得干干净净。单调分支：`count = 60` - 两波都被记住，守卫看到的是上限的 2 倍。

令牌桶补充家族（CUSUM pacing、两个账本）没有单独的测试工具：算术是同一形态，且代码已经带有两道部分防线（`Math.max(0, elapsed)` 防向后跳变，突发上限防向前跳变），因此经审计的影响在那里被限制在"桶提前注满"，而不是窗口被遗忘或翻倍。这句话是代码分析而非测量，并已如此标注。

### 分类

29 个文件的 `src/` 代码树中每一次 `Date.now` / `new Date` / `performance.now` / `hrtime` / 随机数读取，都被追溯到消费它的算术，并按该值的含义（而非变量名）分类：

- **(a) 间隔点 - 必须迁移到单调时钟：12 个。** 其中 10 个是纯内存的（减法的两端都由同一个进程产生，状态只存在于内存中）。2 个是混合型：它们的状态被持久化并跨进程共享，因此单调值不能简单地替换已存储的挂钟时间戳（见第 3 节）。
- **(b) 必须迁移到 CSPRNG 的随机性：0 个。** `Math.random` 在 `src/` 中出现 0 次。现有的安全随机性本来就已是 CSPRNG：金丝雀回声 nonce 是来自 Node `crypto.randomBytes(16)` 的 128 位，传输盾从 `webcrypto.getRandomValues` 获取其 AES-GCM IV 与 nonce。两个确定性的 mulberry32 PRNG（金丝雀迷宫布局、诱饵文档生成）是有意的设计 - 同一条路径必须始终生成同一个迷宫/诱饵 - 被分类为保留，并附带记录在案的边界条件：它们绝不能被复用来铸造 id 或令牌；grep 确认没有任何调用点这样做。
- **(c) 保留挂钟的点：11 组**，每组都有明确的理由（第 4 节）。

## 2. 单调时钟修复

### 锚点：monoNowMs

新的内部文件 `src/internal/mono-clock.ts`（不从 `src/index.ts` 导出）。`monoNowMs()` 返回 `performance.now()` 加上模块加载时捕获一次的锚点：`MONO_ANCHOR_MS = Date.now() - performance.now()`。锚点让单调读数处于与 `Date.now()` 大致相同的量级 - 在日志中比较两者时很方便 - 而任意两个单调读数之间的差值在构造上永不跳变。锚点只是量级上的便利；没有任何语义依赖它，也没有任何持久化状态存储单调值。`createIntervalClock()` 返回拆分的默认对：`{ wall: () => Date.now(), mono: monoNowMs }`。

### 解析规则（resolveIntervalClock）

每个被修补的模块都在现有的 `now` 旁边接受一个新增的可选选项 `monoNow?: () => number`。`resolveIntervalClock({ now, monoNow })` 编码了一条规则：

- 注入 `monoNow` 的宿主显式地驱动间隔域。
- 注入了 `now` 但没有注入 `monoNow` 的宿主，精确保持修补前的单时钟行为：被注入的时钟驱动两个域，因此现有的宿主时钟和测试时钟逐位保持原样。
- 两者都不注入的宿主得到拆分默认值：挂钟用于显示时间戳、日历语义和绝对截止；单调时钟用于每个间隔。

这条规则正是本补丁能以零原有测试修改、零测试损坏落地的原因：每个只注入伪造 `now` 的测试，在两个域中看到的语义完全相同。四个模块（羊群检测器、操作队列、CUSUM 绊线、证据归因）以及两个账本，以内联形式写出同一条规则（`options.monoNow ?? (options.now ? wall : monoNowMs)`），而不是导入辅助函数 - 同一条规则，不同的形式。传输盾的重放守卫使用 `options.monoNow ?? monoNowMs`，因为它的信封时间戳是面向宿主的挂钟值，与注入时钟没有相互作用。蜜罐也由此获得了它以前完全缺失的时钟注入选项（它以前直接调用 `Date.now()`）；它原先唯一的 `now` 变量同时供养每 IP 间隔和 UTC 日历日预算，因此本补丁把它拆成两个来源。

## 3. 两个混合型账本

### 两个截止时间中较早者为准

披露账本和操作预算通过宿主存储持久化其状态，并跨进程共享。单调时间是每进程的，重启即重置，因此不能写入该状态 - 一个被恢复的预留没有有意义的单调出生时间。因此，持久化状态和以前一样精确地保留挂钟截止（`expiresAtMs`、`windowStartMs`、`lastRefillMs`），本补丁在其上叠加了一个进程本地的镜像：一个工厂侧的映射（两个账本中的 `ownReservationMono`）为本进程创建的每一个预留记录其单调创建戳和 TTL。由本进程创建的预留，在其挂钟过期与其单调 TTL 中较早到来的那一个时刻死亡。从存储恢复的、或由另一个进程写入的预留，没有镜像条目，只遵循挂钟截止 - 这一点在 `docs/LIMITATIONS.md` 中写得很清楚，没有隐藏。

### 钳制的补充与窗口锚点

第二个机制限制了跳变对共享算术本身的影响范围。两个账本都根据挂钟流逝时间计算桶的补充，但被计入的流逝时间现在被钳制在 `[0, msToFull]` 内，其中 `msToFull` 是桶按其配置速率完全注满所需的时间：在时钟健康时，这个钳制在数学上是一个无操作（补充本来就被突发大小封顶）；在跳变之下，它把一种隐含行为变成了显式界限 - 向前跳变永远不能计入超过一个满桶的时间，向后跳变永远不能计入负时间。操作预算把同样的思想用于窗口：`windowAnchors` 记录本进程创建或滚动的每个主体/队列窗口的挂钟起点和单调起点，因此这样的窗口即使挂钟跳变也会按其单调长度滚动；一旦已存储的 `windowStartMs` 与锚点不再匹配（另一个进程滚动了该窗口），锚点立即失效，此后该窗口由挂钟支配，直到本进程再次滚动它。

## 4. 保留挂钟的部分

有 11 组保留挂钟读取，这是设计使然，每一组都是因为该值的含义是绝对的或跨方的，而不是一个进程内间隔：

- **签名负载中的过期：** 游标和 cursor-v2 的 `iat`/`exp`、金丝雀回声 id - 嵌入在负载中的绝对截止，另一个进程或实例之后可能对其进行验证；纪元是唯一在跨进程时有意义的时间域。它们的 TTL 有界（游标为 300 秒），把任何跳变的影响封顶在 TTL 之内。
- **运营方签发的有效窗口：** 校准清单的 `issuedAtMs`/`expiresAtMs` 以及受保护队列声明的 `expiresAtMs`/`declaredAtMs` - 一个工件或一份声明的业务有效性是一个绝对陈述（"有效至 X 时刻"），而不是本进程计量的一个间隔。
- **跨机器协议纪元：** RFC 9421 Web Bot Auth 的 `created`/`expires` 是由签名方机器签发的纪元秒；验证必须在挂钟域中比较（已存在 `clockSkewSeconds` 容差）。传输信封的 `ts` 同样是双方之间交换并绑定进 AAD 的纪元；其过期检查是带偏差容差的跨方比较。（只有重放守卫的内部 TTL 记账迁移了 - A9。）
- **日历语义：** 金丝雀迷宫的每日上限是一个 UTC 日历日规则（`toISOString().slice(0, 10)`）；CUSUM 纪元轮转以及羊群/操作形成窗口都运行在宿主提供的事件时间戳之上。
- **显示与出处：** 日志、警报、快照中的 ISO 时间戳以及证据评审者的 `generatedAtMs` 是给人类读者看的；挂钟是正确的域，且它们都不供养任何间隔计算。
- **内容，而非时间：** 诱饵幻象伪造的 `effectiveFrom` 日期是生成的文档内容。
- **宿主提供的时间戳：** 宿主附加的事件 `ts` 值属于宿主的时间域；SDK 的单调时钟无法修复一个提供歪斜时间戳的宿主。SDK 只拥有它自己的 `?? now()` 退路，这些已计入 A4-A6。这是一个覆盖边界，记录在此，以免任何人把本补丁读成"所有时间扭曲都已修复"。

- **修补前证据：** 第 1 节的实验室测试工具在已发布的 2.6.1 `dist` 模块的逐字副本上运行了两次，输出逐字节相同 - 挂钟分支在 10 秒真实时间内服务 200 条记录（预算的 200%），而单调分支守住了预算；挂钟分支下一个已用完的窗口在真实第 360 秒而非第 60 秒解锁，而单调分支按时；配额 `count` 为 30（被遗忘的波次）对 60。
- `npm run benchmark:build-sdk` 通过（本补丁不触及基准测试表面）。

## 6. 剩余限制与本补丁不改变的内容

- **被恢复的与跨进程的状态只有挂钟。** 持久化的账本/预算状态只携带挂钟截止；从存储恢复的、或由另一个进程写入的预留或窗口，没有单调镜像，只遵循挂钟，直到本进程创建或滚动它自己的。镜像是进程本地的映射，从不持久化，也从不共享。这是本设计诚实的边缘：单调时间无法共享，假装可以会破坏账本的跨进程契约。
- **单调时间是每进程的。** `performance.now()` 的分辨率和挂起行为属于平台；锚点只是量级上的便利，对跨越进程重启的间隔不做任何声明。
- **宿主时钟不在范围内。** 宿主提供的事件时间戳和宿主提供的自定义存储运行在宿主的时钟纪律之下；本补丁只消除来自 SDK 自身时钟读取的扭曲。
- **对行为良好的宿主没有行为变化：** 预算、上限、pacing、队列法则、校准默认值和每个已发布的常量都与 v2.6.1 完全相同。注入了自己的 `now` 时钟而没有注入 `monoNow` 的宿主，观察到的 literally 就是修补前的行为。
- **排队中的审计发现不在此修复：** 2.6.0 审计中剩余的 MEDIUM/LOW 发现（F-02 至 F-05、F-08 至 F-11 及其余部分）保持其 v2.6.1 行为，继续排队等待后续轮次，正如 2.6.1 补丁留下它们时一样。
