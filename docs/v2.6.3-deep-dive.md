# v2.6.3 deep dive

## Summary

v2.6.3 is fix wave 2 from the full security audit of the released v2.6.0 tree: the eight remaining MEDIUM findings (F-02, F-03, F-04, F-05, F-08, F-09, F-10, F-11). The HIGH finding and the first three MEDIUMs shipped in v2.6.1, the clock hardening in v2.6.2; the 13 LOW and 4 needs_validation findings are untouched and queued. The wave changed four source modules (`quota-guard.ts`, `export-guard.ts`, `action-budget.ts`, `cusum-tripwire.ts`), added 16 regression tests in `tests/audit-wave2.test.cjs`, and updated four rows of `docs/LIMITATIONS.md`. Contract impact is additive only: one optional store operation, two new refusal reasons, three new options, and new informational fields on existing result types. Suite: 338 tests, 336 pass, 0 fail, 2 pre-existing RSA-PSS skips. Discrimination was verified before shipping: the new test file fails 16/16 against the captured pre-patch dist and passes 16/16 against the patched dist.

## 1. The enforcement gaps in the guards

### F-02: quota checks and writes were two steps (quota-guard)

**The defect.** The quota guard read the store (peek), decided, then wrote (record). With a store whose reads and writes are separate calls, parallel requests can all pass the peek before any of them records, so a burst overshoots the rate limit by however many requests race through the gap.

**The fix.** The store contract gains an OPTIONAL operation `recordIfBelow(key, now, windowMs, limit)` returning `{ recorded, refusal?, count, oldest? }`: prune, compare against the limit and record as one indivisible step (a real backend implements it as a Redis Lua script or a SQL transaction). The bundled in-memory store implements it with the same capacity law as `record` - a fresh window at the key ceiling returns `refusal: "capacity"` and never evicts a live window. The guard's peek phase is unchanged (fast-path rejection plus the F-06 fail-closed discipline); the write phase uses `recordIfBelow` when the store offers it: an at-limit refusal becomes `rate_limit_exceeded` with Retry-After derived from the store's `oldest`, a capacity refusal becomes `store_capacity_exceeded`, and a throwing or malformed store still becomes `store_unavailable`. A store without the new operation takes the pre-patch `record()` path byte-identically - but that fact is no longer hidden: `QuotaGuard.atomicEnforcement` and an `atomicEnforcement` field on every `QuotaCheckResult` state whether the configured store enforces atomically.

**Measured.** A delayed store whose 15 ms delay sits OUTSIDE the atomic operation admits exactly 5 of 12 parallel requests at a limit of 5, and the five admitted carry distinct X-RateLimit-Remaining values {0,1,2,3,4} - evidence that check and record are one step. A legacy peek/record-only store still admits 12/12 exactly as before, now flagged `atomicEnforcement: false` on the guard and on every result.

### F-03: exports had no up-front reservation (export-guard)

**The defect.** Each export preflighted against the same untouched budget. Four exports that each fit alone could all be admitted and jointly overshoot the record cap before any of them settled.

**The fix.** The middleware - the only layer with a settle hook, following the same pattern as the record budget's `reserveUnits` - now reserves `estimatedRows x 2` before `next()` whenever the per-record path is wired (recordBudget + extractRecordIds + identityKey) and `estimatedRows > 0`. The multiplier is the worst case: one unit per record plus one extra for never-before-seen records. A failed reserve returns the guard's own 429 `record_budget_exceeded` body shape and emits `onRejected`. The reservation is released in the settle `finally` on every exit path (json / end / write+end). With no estimate, no reservation is possible - the module already documented "wire an estimate" - and the pure `checkRequest` path is unchanged, because no settle hook exists there.

**Measured.** The audit h7 scenario (ceiling 8, estimate 3 per export, 4 parallel preflights): exactly 1 export admitted, the other 3 refused 429; the admitted handler served 3 distinct records; used = 6 against the ceiling of 8. Pre-patch, the same scenario served 12 distinct records at used 24. After settle, the reservation is provably released - a further small check passes against the freed headroom. One deliberate side effect, documented in the module header and LIMITATIONS: sequential exports tighten to the same invariant, so an export whose worst case does not fit the remaining budget is refused even when its true cost would be 0 (all records previously exported).

### F-04: CSV and streamed bodies priced at zero (export-guard)

**The defect.** The settle hook only priced bodies it could `JSON.parse`. A CSV body parse-fails quietly, so CSV exports settled at 0 units. In the audit's live test, a CSV export pulled 150 records through a ceiling of 60 while the budget never moved.

**The fix.** The middleware now also wraps `res.write`, collecting string and byte chunks up to a cap of ~1M characters; past the cap the body is remembered as not per-record-priceable instead of being buffered without bound. Settlement happens at `end()` over the WHOLE body (collected chunks plus the end body): if it parses as JSON, per-record pricing applies exactly as before; if it does not parse (CSV, text, streams), the price is the flat `ceil(estimatedRows x budgetMultiplier)` - the same price the flat path charges for the same row count. With no estimate, the charge is the new option `unpricedBodyFloorUnits` (default 1; set 0 to disable). `res.send` flows through `end`, so it is covered - verified against Express semantics, the audit's mock and the live sample host.

**Measured.** The audit harness h4 on the patched build: JSON 6, CSV via `end` 6, CSV via `send` 6, streamed CSV 6 - pre-patch 6/0/0/0. Live retest on the audit's sample host in protected mode: CSV answers `[200, 429, 429, 429, 429, 429]`, the same schedule as JSON, once the budget is spent.

## 2. Pricing and delivery semantics

### F-05: an unpriced action was free forever (action-budget)

**The defect.** Price resolution fell through to 0: an action the host never priced - no explicit cost, no price-table entry - was granted at zero cost, forever, in enforce and audit_only modes alike.

**The fix.** Resolution is rewritten: an explicit finite host cost wins; then the price table; an action with NEITHER is refused with the new reason `unknown_action`, returned before the store transaction opens (pure validation - no state is read or written - applied identically in both modes). A host that prefers a fallback price sets the new option `unknownActionCost`: unknown actions are charged that price and every affected result carries `unpriced: true`. Deliberate zeros are untouched: an explicit `cost: 0` or a price-table entry of 0 passes normally, with no flag. A non-finite explicit cost (NaN, Infinity) no longer silently degrades to 0 - it falls through to the table and then to the unpriced path.

**Measured.** The audit V3 scenario: 30 of 30 unpriced attempts refused `unknown_action` (pre-patch: 30 granted). With `unknownActionCost: 7` against an allowance of 10, the first reserve commits at cost 7 flagged `unpriced: true`; the second is refused `subject_budget_exceeded`, still flagged; the commit path works end to end.

### F-08: a throwing flag callback lost the flag (cusum-tripwire)

**The defect.** `onCampaignFlag` was invoked bare at the crossing. If the host's callback threw, `observe` threw with it - and the flag, which existed only as that single delivery attempt, was gone. The host's `isProtected` / `isExempt` predicates were also called bare, so a throwing predicate propagated into the host's request path.

**The fix.** Predicates are wrapped (`safeIsExempt` / `safeIsProtected`): a throwing predicate behaves as an absent predicate, the error swallowed - the same pattern the sibling herd, flow and action-cohort modules already used - at every call site: the head of `observe`, the `snapshotOf` filter, `protectedHere` and `checkServe`. The flag itself is now state, not an attempt: a cohort carries `flagNotificationPending`; a crossing sets the mark FIRST, then `deliverFlag()` tries the callback with a freshly built snapshot; success clears the mark, a throw keeps it. Retry points are the cohort's next `observe` (at most one attempt per observe, never a second attempt inside the crossing call itself) and `getSnapshot` / `snapshotFor`. Epoch rotation and `clearCohort` cancel a pending notification together with the flag.

**Measured.** The audit harness h5 H2-2 after the patch: `observeThrew: false`, `secondObserveThrew: false`, `callbackCalls: 3`, `snapshotFlagged: true` (pre-patch: observe threw and the flag was lost). The regression tests cover delivery on the next observe, delivery on the next snapshot read, and throwing predicates behaving as absent (the crossing still escalates to step_up, `protectedMembers` reads empty, `checkServe` does not throw).

### F-09: checkServe(NaN) poisoned a cohort bucket (cusum-tripwire)

**The defect.** `checkServe(identity, NaN)` fed NaN into the pacing bucket's arithmetic. Every later refill computed with NaN, `Math.min` could never wash it out, and the cohort's bucket stayed dead - `allowed: null` on every subsequent call - until the process restarted.

**The fix.** All three layers the audit required. (1) Validation at the very head of `checkServe`, before any early return: a `requested` that is not a finite number, or is negative, returns the structured refusal `{ allowed: 0, reason: "invalid_request" }` (with `cohortId` when a cohort exists), mutates NO state and never throws; `requested = 0` remains a valid no-op. (2) `refill()` self-heals: a non-finite `bucketTokens` resets to burst, and tokens are clamped into [0, burst] after every refill. (3) `clearCohort` now also resets the bucket (tokens = burst, fresh refill anchor) - the old clear left a poisoned bucket poisoned.

**Measured.** The audit harness h5 H2-5 sequence on a flagged, eligible cohort with a fixed clock: serve 10; NaN refused `{allowed: 0, reason: "invalid_request"}` (the same for -5 and +/-Infinity); serve 10; serve 10. The snapshot reads `bucketTokens = 130` (150 - 10 - 10, nothing leaked). After `clearCohort` the bucket reads the full 150. Pre-patch on the same harness: NaN returned `allowed: null`, and every later call returned `null` - the bucket never recovered.

## 3. State that never reset and never stopped growing

### F-10: bounded identity state with LRU eviction

**The defect.** The tripwire kept per-identity state (scores, pair-throttle entries, predicate rings) in maps that only grew. A long-lived process watching many identities paid more per event the longer it ran, with no ceiling and no cleanup.

**The fix.** The module gains the option `maxIdentities` (default 2000, minimum 10), following the herd detector's shipped pattern. `identityState()` refreshes an identity's LRU position on every hit; creating state at the cap evicts the least-recently-active identity through `removeIdentity`: the victim's singleton state, pair-throttle entries and predicate ring are removed, and the victim is pulled out of its cohort (`members`, `contributions`); if the victim is the union-find root, another member is promoted, the cohort is re-keyed and `cohort.id` recomputed (the same surgery `mergeIdentities` uses); an emptied cohort is deleted. Members of host-DECLARED cohorts are evicted last - the host named them on purpose. The two pair-throttle maps now carry `{ size, atMs }` values: entries older than `formationWindowMs` are treated as absent and deleted on read (TTL), and each map has a size backstop of `max(1024, maxIdentities x 4)` trimmed oldest-insertion-first. `CampaignSnapshot` gains the additive field `stateSizes: { identities, cohorts, pairThrottles }`, so an operator can watch the caps hold.

**Measured.** With the cap at 10, an active two-slicer cohort survives a churn of 30 singletons with both members intact, and `stateSizes.identities` reads 10 after 32 distinct identities. Evicting quiet cohort members - including the union-find root, which triggers promote-and-rekey - leaves a working engine: no throw, no ghost cohort, and the evicted pair can form again afterwards. One nuance, stated openly: the pair-throttle TTL means a pair may be re-evaluated after its window even without `recheckGrowth`; the merge decision is still gated by every formation criterion, so this costs compute, never looser criteria.

### F-11: epoch rotation now resets score and contributions

**The defect.** When a cohort's evidence epoch rotated, its accumulated CUSUM score and per-member contributions stayed. The first event of the new epoch re-crossed the boundary immediately on stale evidence, flagged the cohort again, and aimed consequences at contributors from the previous epoch.

**The fix.** The rotation block now sets `cohort.score = 0`, clears `cohort.contributions` and cancels `flagNotificationPending` - an epoch is an evidence window, per the interface's own docstring. Union coverage and served counts are deliberately NOT reset: coverage is a real event and the consequence floor reads it. Singleton scores are outside the finding (singletons carry no flag and no consequences) and are unchanged.

**Measured.** The audit h6 control: a cohort that crossed at ts=1,000,000 (with account:b among its contributing members and score at or above the boundary) sees, at its first event +90 days: `crossed: false`, `score: 0`, no account:b in the snapshot's contributing members, `consequenceTargets(...).targets = []` - and `unionRecords = 165` (160 + 5 new), coverage preserved. The h5 control reads the same way: `flagged: false` after +90 days. Pre-patch, both controls re-crossed instantly on the rotated-but-stale score.

## 4. Contract additions

Everything in this wave is additive; no existing signature, reason or default changed meaning.

- **Store contract (quota-guard):** one OPTIONAL operation, `recordIfBelow(key, now, windowMs, limit)` returning `{ recorded, refusal?: "capacity", count, oldest? }`. Stores that implement it get atomic enforcement; stores that do not keep the pre-patch behavior exactly.
- **New refusal reasons:** `unknown_action` (action-budget: the action has no price and no fallback was configured) and `invalid_request` (cusum-tripwire `checkServe`: the requested amount is not a finite, non-negative number). The atomic quota path also surfaces `store_capacity_exceeded` for a store capacity refusal.
- **New options:** `unknownActionCost` (action-budget fallback price), `unpricedBodyFloorUnits` (export-guard flat charge when no estimate exists; default 1), `maxIdentities` (cusum-tripwire state cap; default 2000, minimum 10).
- **New informational fields:** `atomicEnforcement` on every `QuotaCheckResult` and on the guard itself; `unpriced: true` on action-budget results charged through the fallback; `stateSizes: { identities, cohorts, pairThrottles }` on `CampaignSnapshot`.
- **Docs:** `docs/LIMITATIONS.md` gains four rows matching the new behavior (quota enforcement modes, the export reservation trade-off, CUSUM state bounds and flag delivery, action-budget unknown actions).

- **Suite:** 322 → 338 tests (336 pass, 0 fail, 2 pre-existing RSA-PSS skips). The delta is `tests/audit-wave2.test.cjs`: 16 regression tests, at least one per finding. Zero pre-existing tests were modified, and none were loosened.
- **Discrimination:** the new test file was run against the captured pre-patch dist before the wave closed: 16/16 FAIL on pre-patch behavior, 16/16 PASS on the patched build. No test is green-by-construction.
- **Audit harness retests on the patched build:** V3 (unpriced actions) 0/30 granted; V5 (delayed legacy store) 12/12 admitted with `atomicEnforcement: false`, while a delayed store WITH the atomic operation admits exactly 5/12 at a limit of 5; h4 (export pricing matrix) 6/6/6/6; the live sample host answers CSV `[200, 429, 429, 429, 429, 429]`, the JSON schedule; h5 H2-2 no throw with the flag intact; h5 H2-5 serve 10 → invalid → 10 → 10; h6 and the h5 +90-day controls read `flagged: false`; the h7 variant admits 1/4 preflights with used 6 / distinct 3 against a ceiling of 8 (pre-patch: 12 distinct, used 24).

## 6. Remaining limits and what this patch does not change

- **Legacy stores keep legacy behavior.** A host store without `recordIfBelow` still admits the F-02 race exactly as before - the change is that the guard now DECLARES it (`atomicEnforcement: false`) instead of implying a hard guarantee. The audit's own V5 harness still reports 12/12 for this reason: its delayed wrapper store implements only peek/record, which is precisely the legacy store class. The audit report's section 8 criterion (delayed store + 12 parallel requests → exactly 5 admitted) is met with a delayed store that HAS the atomic operation; adding the operation plus the honesty flag is the minimal fix shape the audit itself proposed, not a sidestepped criterion. Atomicity is also per dimension/key: if a later dimension refuses, an earlier dimension's recorded hit stays, exactly the legacy semantics; multi-key transactions are out of scope.
- **No real distributed store was measured.** `recordIfBelow` is verified on the bundled in-memory store and on a delay-wrapped model of it. No Redis or SQL backend exists in this environment; the contract places the atomicity obligation on host implementations.
- **F-16 (LOW) is not patched.** `observe()` still does not validate event input. The concrete symptom from the audit harnesses: an event with a NaN timestamp never rotates its epoch (every comparison against NaN is false), so the h5/h6 ts-NaN variant keeps its pre-patch behavior. This variant was already rejected by the audit's verifier as a standalone finding - it is the input-validation domain, and it needs one contract decision (a silent, counted drop vs a deliberate throw) before it can be fixed honestly. It is queued for the next wave.
- **The rest of the audit queue stands.** 13 LOW and 4 needs_validation findings are untouched by this wave. The wave-2 fix report names the cheapest safe candidates for the next wave (F-20, F-12, F-16, F-15) and the ones that should not be rushed (F-13, F-14, F-17, F-18, F-19, F-21, F-22, F-23, F-24).
- **Per-fix residuals, stated by the fix report:** an export handler that never settles its response holds its F-03 reservation until the budget window rolls, and a response object with no write/end/json surface has no settle point; a JSON export body above ~1M characters is charged the F-04 flat price by design; `checkServe` is not an F-08 flag retry point, and a cohort never touched again keeps its notification pending (no timer, by design); the F-10 fallback path that evicts a declared-cohort member when EVERY identity is declared has no dedicated test, and pair-throttle TTL performance on large traces is unmeasured; F-11 leaves singleton scores un-rotated, outside the finding's scope.
- **One harness defect is the audit's, not the SDK's:** the audit's h5.cjs crashes at its line 76 (reading `.subjects` of a null raw store, block H1-5) identically on the pre-patch and patched dists, after every item this wave touches has already printed. It was left as found.
