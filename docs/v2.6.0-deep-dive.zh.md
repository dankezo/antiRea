# v2.6.0 深入解析

v2.6.0 版本的完整技术说明。主 README 保留简短的通俗摘要；以下为详细版本。

## v2.6.0 新功能：操作预算、操作群体与金丝雀操作 - 功能滥用层

2.5.0 版本计量的是*数据*一侧：一个身份 - 或一个协同的身份群体 - 能收到多少条不同记录。2.6.0 版本为*功能*一侧加上了镜像层。威胁模型在一个关键点上不同：攻击者*正确地*使用功能。请求有效，会话真实，没有违反任何协议。滥用是聚合性的 - 许多廉价身份，每个都待在自己的个人限额之内，共同耗尽一项共享资源：昂贵端点上的主机计算和带宽、一个有限的促销或试用池，或者对一个昂贵操作的简单公平性。记录预算看不到这一点，因为被消耗的是操作本身，而不是它返回的记录。两层都适用；没有一层取代另一层。

该层附带三个机制 - 操作预算、操作群体跟踪器和金丝雀操作 - 遵循与 SDK 其余部分相同的纪律：**没有事务，就没有执行；仅凭推断证据，绝不施加硬性后果。**

## 1. 操作预算 (`createActionBudget`)

### 主机声明的价格

主机声明一张价格表：每种操作类型的抽象成本单位（导出、繁重搜索、促销领取等等）。SDK 从不发明价格 - 一个操作值多少成本是主机的业务事实，不是库常量。预留请求也可以携带一个显式的主机计算成本，它会覆盖该次调用的表项。

### 在披露账本的存储合同上预留 / 提交

难点与披露账本的完全相同：每主体限额加上已声明群体的聚合上限，只有在检查与预留是原子的时候，才可执行。因此操作预算运行在与 `createDisclosureLedger` **相同的 `LedgerStoreAdapter` 合同**上 - 适配器和附带的存储是导入的，从不分叉。状态有命名空间（`action-budget:<budgetId>`），使一个操作预算和一个披露账本可以共享一个存储而不冲突。

- 实现 `transactLedger` 的存储（对状态版本做 CAS，在一个事务中覆盖限额、预留、上限、桶和证据累加器）以 `mode: "enforce"` 运行。
- 只有 get/put 的存储以 `mode: "audit_only"` 运行：每个决定都带有 `enforced: false`，决定是尽力计算的，并行预留**可以**共同超支。该模块报告这一点，而不是隐藏它。在 audit_only 模式下，唯一的承诺是账本本身的诚实 - 记录了什么 - 而不是阻止。

预留遵循账本的边界，为操作重新命名：预留 -> 提交 / 释放，TTL 在事务内部惰性过期（默认 60 s），默认每个主体最多 2 个未完成预留和 500 的预留成本，可选的群体级未完成上限，幂等键，以及为慢速操作提供的单独的主机授权长预留路径（15 分钟 TTL）。预留花掉的桶令牌在释放时**不退还** - 节奏是成本，不是押金。

### 已声明群体上限，在声明时武装

主机声明的操作群体的上限**在声明时武装** - 把 2.5.0 的声明时上限规则应用到操作上。成员的预留从第一个操作起就计入该群体在每个窗口内的上限；不需要标记、越界或预热。以该群体 id 预留的非成员会被拒绝为 `unregistered_subject`，未声明的群体 id 会被拒绝为 `unknown_cohort` - 两者都失败关闭。重新声明一个群体更新成员和上限，但**不会**重置其窗口记账：重新声明绝不能洗掉已经计数的成本。

### 节奏桶

两个令牌桶控制流量：一个覆盖该预算全部预留的全局桶，以及通过 `setCohortPacing` 应用的可选的每群体节奏项。节奏拒绝是一个带 `retryAfterMs` 的 `rate_limited` 结果 - 是一种速率，绝不是永久拒绝，也绝不触碰未列入该节奏项的主体。

## 2. 操作群体跟踪器 (`createActionCohortTracker`)

预算计量一个身份可以花多少。跟踪器观察每身份预算看不到的维度：一*组*身份的操作在聚合上覆盖了什么。它是群体检测器的两个分组机制从记录空间转置到操作目标空间 - 一个操作的目标是导出的切片 id、搜索范围覆盖的语料切片、促销 id，或者一般地说，端点 id。

### 互补分组

目标集合在同一操作类别上近乎不交、且并集很大的身份被分到一组：一个导出空间的不交切片，一个语料的不交范围。分组是**基于领导者的**，与 herd v2 一样：一个身份的组会与其它组的*聚合*比较（每组一个目标引用计数映射），从不与每一个其它身份比较，也没有每对状态。一个身份只有在加入其目标之后，该组的重叠比例（`1 - distinctTargets / totalTargetInstances`）保持在不高于关联上限（默认 0.10）时，才加入该组。只有在尾随窗口内活跃的身份（默认 15 分钟）才计数。

**稀释门控**是形态定义：一次互补标记要求该组至少 **60%** 的成员在尾随窗口内各自处于或低于其主体限额。该组之所以危险，恰恰是因为没有成员危险；成员各自超过其限额的组（一个小型重型团队）不会被互补标记 - 每主体预算管辖它。

### 共享目标分组

汇聚到同一个 `targetKey` 的身份 - 一个促销、一个端点 - 是 farming 形态，此时目标集合是相同的，而不是互补的。互补分组会正确地拒绝合并它们（它们的重叠是最大的），因此这个机制改为计算每个目标的不同主体数和聚合成本。共享目标标记**不**要求稀释门控：促销池是被各自合法的领取耗尽的。

### 重要性和摩擦定位

重要性是每个维度的标记下限的 1/12，向上取整，最小为 1 - 群体规则的推导。它的*应用*方式取决于机制（下文第 5 节的 Fix B）：

- **互补：** 成员的重要性是其**唯一目标贡献** - 组内没有其他人持有的目标。仅凭原始成本，永远不会使一个互补成员具有重要性。
- **共享目标：** 成员的重要性是其**成本**，因为其贡献是那一个共享目标上的量。

对于补充重新宣告，重要性保持为成本或唯一贡献，与数据一侧一样。当一个尚未以重要贡献被宣告过的成员 - 迟到的加入者，或一个待定的部分贡献者 - 跨过重要性时，被标记的组会重新宣告自己（补充快照，每组每 5 s 最多合并为一个）。一个以恰好零贡献被宣告的成员就是已沉降不活跃的，永远不会自行重新触发。

`actionFrictionTargets()` 只保留重要成员，**再减去受保护成员**：被标记组内的旁观者获得零摩擦，与数据一侧一样。受保护主体积累完整遥测，并列在 `protectedMembers` 之下。

### IP 从不是分组键

IP 被记录在事件上，但**从不**是分组键。只共享一个 IP、操作和目标互不相关的身份，永远不会分组，也永远不会被标记 - 与数据一侧一样，这是一个有单元测试的不变量。

### 跟踪器从不阻止

与群体检测器一样，跟踪器从不阻止、封禁或改变响应。它发出 `onFlag` 快照；后果由主机决定，对于推断群体，要经过分层钳制（第 4 节）。

## 3. 金丝雀操作 (`createCanaryActionRegistry`)

主机注册合法 UI 从不发出的目标键：一个从不被链接的导出切片，一个从不被展示的促销 id。一次触碰是**直接的每主体证据**：跟踪器只为触碰的主体记录一个污染。

- 污染从不溅到其他主体身上。
- 受保护主体自身的金丝雀命中仍然会污染该主体 - 声明不是洗白通道。
- 归属来自请求上已认证的主体，因此金丝雀目标无法被用来嫁祸另一个主体：触碰被记录在触碰它的人身上。
- 当污染存活时（跟踪器的活动窗口），被污染主体会出现在同一操作类别上任何标记快照的 `taintedMembers` 中，条件是它是该组的成员**或**其目标与该组的目标相交。因此，轮换到一个全新身份在第一次金丝雀触碰时就不再重置时钟：伸向同一表面的新身份会通过污染把自己关联到被标记群体。

## 4. 后果规则 - 与数据一侧相同的分层规则

功能一侧的后果完全遵循数据一侧的规则，转置如下：

- **推断群体**（跟踪器标记）的上限为：**观察 + step-up 摩擦 + 一个带下限的软性预算下调**。下限是*推导*出来的，不是选出来的：`derivedSoftFloorCost` 是主机表中单个操作的最高价格 - 是 `SOFT_BUDGET_FLOOR_RECORDS` 的直接转置（它本身源自披露账本的每主体预留上限）。被下调的主体始终在每个窗口内恰好保留**一个最大的合法操作** - 最昂贵的单个操作的价格。是摩擦，绝不是扼杀。
- **硬性锁定**（下调到 0、硬性上限）需要一个**主机声明的群体，或一个 ceiling 层级校准清单** - 主机自己的授权决定，绝不只是推断。`clampActionStepDown()` 把层级决定委托给 `clampEnforcement()`，并为推断群体应用推导出的下限；把推断群体削减到零的要求会被钳制回下限，即使配置要求这样做，也会在代码中被拒绝。

## 5. 修复轮次 - 三个设计修复，没有改动任何常量

功能经典轮次的第 1 轮（第 6 节）没有通过其完成分数线，并有一个金丝雀子检查失败。修复轮次改的是**设计，不是常量** - 以下每个附带默认值都是第 1 轮的值。

- **Fix A - 尝试时评估（`evaluateAction`）。** 对跟踪器的一次纯查询：不记录任何东西，不改变任何状态，不触发 `onFlag`，不记录污染，因此主机可以在提供一个操作*之前*调用它，并可自由重复调用。它针对该事件操作所属的每个互补组，报告该事件是否会加入该组、该组是否已被标记，以及该事件的目标是否已被该组知晓（`targetKnown`）。主机侧的后果：一个正走向已被标记的组、朝向一个**新**目标的加入者，会在**尝试时**被 enroll - 在它生成标记时 enroll 以前要等待的成员观察之前。
- **Fix B - 取决于机制的重要性。** 如第 2 节所述：互补的摩擦定位只计算唯一目标贡献；共享目标保持基于成本。第 1 轮的金丝雀失败是直接动因：原始成本重要性把一次成本为 10 的导出算到 9 的下限之上，一个旁观者凭一个别人也持有的目标就被 enroll 并被覆盖。
- **Fix C - 节奏桶在成员变化时保留已花状态。** 对同一范围重新应用群体节奏，会更新成员和桶参数，但**保留桶的令牌和补充时钟**。修复之前，一次成员变化可能把一个已经耗尽其突发量的群体再递上一份新的突发量；修复之后，扩大主体列表永远不会重置节奏。

### 修复轮次两条 FAIL 线的分类

- **F1 标记并集（14/24 对 16 的分数线） - 测量脚本与架构不匹配。** Fix A 在*尝试时* enroll 一个加入者，在它生成成员观察之前。标记并集计数器计算被标记组内的观察，因此尝试时 enroll - 修复按设计工作 - 在机制上降低了该计数器能达到的值。以直接方式、按 enroll 衡量的摩擦覆盖是 **24/24**。这条线被记录为 FAIL，因为它就是按预先登记的原文登记的；分类解释了未达标，它并不抹除它。
- **F2c 窗口内完成 - 附带节奏常量的数学边界。** 测试工具的节奏桶以 0.1 令牌/s 补充，对着 10 的导出价格：突发之后，整个群体以大约**每 100 s 1 次导出**的速度补充。以这个公布的速率，一旦摩擦介入，40 次操作不可能在 15 分钟窗口内完成。关键在于，从来没有任何东西被硬性拒绝：3,205 次尝试中 0 次硬性拒绝 - 工作以受限的速率流动，而不是停止。这是主机为该轮次选择的常量的一个性质，在此说明，使选择相同常量的主机能预测相同的算术。单独的 75 分钟确认运行已经完成：同一个团队在 **47 分钟 40 秒**内完成了同一份工作 **40/40**（2,860,482 ms；7,222 次尝试；3,322 x 401，480 x `subject_budget_exceeded`，3,380 x `rate_limited`；0 次硬性拒绝；测得的服务速率稳定在每 10 分钟 6 次导出，与上文算术相符）。因此上文的窗口内 FAIL 作为窗口假象成立，而该单元旨在探查的最终完成性质，在常量所要求的窗口处得到确认。

与 F1 基线对照 - 无保护时 80/80 次操作在 241 ms 内完成、0 次中断 - 受保护一侧把同一类工作变成了 220 次尝试和 108 次中断，且没有在驱动上限内完成它，每一个参与身份都被 enroll。这就是该层的经济学主张，也是它的全部主张：滥用变得更慢、更可见、每单位结果更昂贵。这不是在宣称该工作变得不可能。

## 9. 这一层不覆盖什么

- **经典驱动是脚本化的。** 本轮次没有对功能一侧运行 REA 驱动或 LLM 驱动的攻击者。这些数字证明对脚本化形态的机制，而不是对自适应智能体的检测率。
- **附带的存储是内存中的、单进程的。** 执行的精确性是在该接线下证明的。分布式存储尚未被证明：运行多个进程的主机必须提供一个实现同一 CAS 合同的存储，在做到这一点之前，适用 audit_only 的诚实规则。
- **S2（繁重搜索）已接线并定价，但没有自己的攻击单元。** 操作预算为搜索操作定价，跟踪器观察它们；没有经典单元专门攻击搜索表面，因此不为它宣称任何单元结果。
- **S3（注册 + 促销 farming）只在单元测试和接线级别覆盖。** 共享目标机制和金丝雀注册表有单元测试并已接线；没有专门的 S3 经典单元，因此不为它宣称任何经典结果。
- **污染过期和共享目标补充路径已写代码，但没有专门的单元测试。** 污染在构造上存活于跟踪器的活动窗口，共享目标组实现与互补组相同的补充重新宣告纪律；本版本中两种行为都没有自己的测试，两者都在此说明，而不是被默默假定为已覆盖。
- **audit_only 竞态是设计边界，不是 bug。** 在 get/put 存储之上，该层承诺的是账本的诚实 - 决定标有 `enforced: false`，超支在记录中可见 - 并明确**不**承诺在并发下阻止。
- **业务逻辑的正确性不在范围内。** 一个价格是否计算正确、一个库存扣减是否竞态安全、一个对象是否属于请求者（IDOR / 授权）、输入是否防注入、或者认证逻辑是否健全，都是主机代码缺陷。计量层无法检测或修复它们，本版本中的任何内容也不作相反的宣称。

本版本的套件：**298 个测试 - 296 通过，0 失败，2 跳过**（先前存在的 RSA-PSS 向量）。
