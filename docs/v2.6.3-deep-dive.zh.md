# v2.6.3 深入解析

## 概述

v2.6.3 是对已发布的 v2.6.0 代码树进行全面安全审计后的第 2 波修复：剩余的八个 MEDIUM 级别发现（F-02、F-03、F-04、F-05、F-08、F-09、F-10、F-11）。HIGH 级别发现与前三个 MEDIUM 已在 v2.6.1 中发布，时钟加固在 v2.6.2 中发布；13 个 LOW 与 4 个 needs_validation 发现未被触及，仍在队列中。本波修改了四个源模块（`quota-guard.ts`、`export-guard.ts`、`action-budget.ts`、`cusum-tripwire.ts`），在 `tests/audit-wave2.test.cjs` 中新增 16 个回归测试，并更新了 `docs/LIMITATIONS.md` 的四行。契约影响纯粹是附加性的：一个可选的存储操作、两个新的拒绝原因、三个新选项，以及现有结果类型上的新信息字段。测试套件：338 个测试，336 个通过，0 个失败，2 个先前存在的 RSA-PSS 跳过。发布前已验证区分度：新测试文件在捕获的补丁前 dist 上 16/16 失败，在已打补丁的构建上 16/16 通过。

## 1. 守卫中的执行缝隙

### F-02：配额检查与记录曾是两个步骤（quota-guard）

**缺陷。** 配额守卫先读取存储（peek）、作出决定、然后再写入（record）。当存储的读取与写入是分开的两次调用时，并行请求可以在任何一个请求记录之前全部通过 peek，于是突发流量会越过速率上限，超出量正是挤进缝隙的请求数。

**修复。** 存储契约新增一个可选操作 `recordIfBelow(key, now, windowMs, limit)`，返回 `{ recorded, refusal?, count, oldest? }`：修剪窗口、与上限比较并记录，三者构成一个不可分割的步骤（真实后端用 Redis Lua 脚本或 SQL 事务实现）。自带的内存存储以与 `record` 相同的容量规则实现它 - 当 key 的容量已达上限时，新窗口返回 `refusal: "capacity"`，且从不淘汰仍存活的窗口。守卫的 peek 阶段保持不变（快速路径拒绝加上 F-06 的失败关闭纪律）；写入阶段在存储提供该操作时使用 `recordIfBelow`：达到上限的拒绝变为 `rate_limit_exceeded`，Retry-After 由存储的 `oldest` 推导；容量拒绝变为 `store_capacity_exceeded`；存储抛错或返回畸形数据仍然变为 `store_unavailable`。没有新操作的存储走补丁前的 `record()` 路径，与之前逐字节相同 - 但这一事实不再被隐藏：`QuotaGuard.atomicEnforcement` 以及每个 `QuotaCheckResult` 上的 `atomicEnforcement` 字段会明说所配置的存储是否以原子方式执行。

**实测。** 一个延迟为 15 ms 且延迟位于原子操作之外的存储，在上限为 5 时从 12 个并行请求中恰好放行 5 个，且获准的 5 个携带互不相同的 X-RateLimit-Remaining 值 {0,1,2,3,4} - 证明检查与记录是一个步骤。只有 peek/record 的旧式存储仍然和以前一样放行 12/12，现在在守卫和每个结果上都被标记为 `atomicEnforcement: false`。

### F-03：导出没有预先预留（export-guard）

**缺陷。** 每个导出都对同一份未被动过的预算做预检。四个各自单独看都装得下的导出可以全部被放行，并在任何一个结算之前共同越过记录上限。

**修复。** 中间件 - 唯一拥有结算钩子的层，沿用记录预算 `reserveUnits` 的同一模式 - 现在只要启用了逐记录路径（recordBudget + extractRecordIds + identityKey）且 `estimatedRows > 0`，就在 `next()` 之前预留 `estimatedRows x 2`。这个倍数是最坏情况：每条记录一个单位，外加一条从未见过的记录一个单位。预留失败会返回守卫自己的 429 `record_budget_exceeded` 正文形态并发出 `onRejected`。预留在结算的 `finally` 中在每条退出路径（json / end / write+end）上释放。没有估算就无法预留 - 该模块先前已在文档中写明"请接入估算" - 纯 `checkRequest` 路径保持不变，因为那里不存在结算钩子。

**实测。** 审计的 h7 场景（上限 8，每个导出估算 3,4 次并行预检）：恰好 1 个导出获准，其余 3 个被 429 拒绝；获准的处理程序提供了 3 条不同记录；used = 6，上限为 8。补丁前，同一场景提供了 12 条不同记录，used 为 24。结算后，可证明预留已被释放 - 一次小的追加检查正好能用上腾出的余量。一个有意保留的副作用，已写入模块头与 LIMITATIONS：顺序导出同样被收紧到这一不变量，因此一个最坏情况装不进剩余预算的导出，即使其真实成本为 0（所有记录都曾导出过），也会被拒绝。

### F-04：CSV 与流式正文被计为零价（export-guard）

**缺陷。** 结算钩子只为能被 `JSON.parse` 的正文定价。CSV 正文会悄无声息地解析失败，于是 CSV 导出以 0 单位结算。在审计的实测中，一次 CSV 导出越过 60 的上限取走了 150 条记录，而预算纹丝未动。

**修复。** 中间件现在还包装了 `res.write`，收集字符串与字节块，上限约为 1M 个字符；超过上限后，正文被记为不可逐记录定价，而不是无限期地缓存在内存中。结算在 `end()` 时对整个正文进行（已收集的块加上 end 的正文）：能解析为 JSON 时，逐记录定价与之前完全相同；不能解析时（CSV、文本、流），价格为统一价 `ceil(estimatedRows x budgetMultiplier)` - 与统一路径对相同行数收取的价格相同。没有估算时，收取新选项 `unpricedBodyFloorUnits` 的值（默认 1；设为 0 可禁用）。`res.send` 流经 `end`，因此也被覆盖 - 已对照 Express 语义、审计的 mock 以及真实样例宿主验证。

**实测。** 审计工具 h4 在已打补丁的构建上：JSON 6，CSV 经 `end` 6，CSV 经 `send` 6，流式 CSV 6 - 补丁前为 6/0/0/0。在审计样例宿主的 protected 模式下重新实测：CSV 的回答是 `[200, 429, 429, 429, 429, 429]`，与 JSON 相同的节奏，一旦预算耗尽即被拦截。

## 2. 计价与送达语义

### F-05：未定价的操作曾永远免费（action-budget）

**缺陷。** 价格解析会一路落到 0：一个宿主从未定价的操作 - 没有显式成本，也没有价格表条目 - 会以零成本被授予，永远如此，在 enforce 与 audit_only 两种模式下都一样。

**修复。** 价格解析被重写：显式的有限宿主成本优先；其次是价格表；两者皆无的操作现在以新原因 `unknown_action` 被拒绝，且在存储事务打开之前就返回（纯验证 - 不读不写任何状态 - 在两种模式下一致应用）。偏好兜底价格的宿主可设置新选项 `unknownActionCost`：未知操作将按该价格收费，且每个受影响的结果都携带 `unpriced: true`。有意的零价不受影响：显式的 `cost: 0` 或价格表条目 0 正常通过，不带标志。非有限的显式成本（NaN、Infinity）不再悄悄退化为 0 - 它会继续落到价格表，然后落到未定价路径。

**实测。** 审计的 V3 场景：30 次未定价尝试中 30 次被以 `unknown_action` 拒绝（补丁前：授予 30 次）。在配额为 10、`unknownActionCost: 7` 时，第一次 reserve 以成本 7 提交并带 `unpriced: true` 标志；第二次被以 `subject_budget_exceeded` 拒绝，仍带标志；提交路径端到端可用。

### F-08：抛错的标记回调会丢失标记（cusum-tripwire）

**缺陷。** `onCampaignFlag` 在越界点被裸调用。如果宿主的回调抛错，`observe` 会随之抛错 - 而那个只以这一次送达尝试的形式存在的标记就此消失。宿主的 `isProtected` / `isExempt` 谓词也被裸调用，因此抛错的谓词会直接传播到宿主的请求路径中。

**修复。** 谓词被包装起来（`safeIsExempt` / `safeIsProtected`）：抛错的谓词表现为缺席的谓词，错误被吞掉 - 这正是同级的 herd、flow 与 action-cohort 模块已经在用的模式 - 并应用于每个调用点：`observe` 开头、`snapshotOf` 的过滤器、`protectedHere` 与 `checkServe`。标记本身现在是状态，而不是一次尝试：群体携带 `flagNotificationPending`；越界时先设置该标记，然后 `deliverFlag()` 用一份新建的快照尝试回调；成功则清除标记，抛错则保留标记。重试点是该群体的下一次 `observe`（每次 observe 最多尝试一次，绝不在越界的那次调用内部再试第二次）以及 `getSnapshot` / `snapshotFor`。周期轮换与 `clearCohort` 会连同标记一起取消待送达的通知。

**实测。** 审计工具 h5 的 H2-2 在补丁后：`observeThrew: false`、`secondObserveThrew: false`、`callbackCalls: 3`、`snapshotFlagged: true`（补丁前：observe 抛错且标记丢失）。回归测试覆盖了在下一次 observe 时送达、在下一次读取快照时送达，以及抛错谓词表现为缺席（越界仍升级到 step_up，`protectedMembers` 读为空，`checkServe` 不抛错）。

### F-09：checkServe(NaN) 毒化群体桶（cusum-tripwire）

**缺陷。** `checkServe(identity, NaN)` 把 NaN 喂进了节奏桶的运算。此后每次补充都带着 NaN 计算，`Math.min` 永远无法将其洗掉，群体的桶就此死透 - 此后每次调用都返回 `allowed: null` - 直到进程重启。

**修复。** 审计要求的三层全部到位。（1）在 `checkServe` 的最开头、任何提前返回之前做验证：`requested` 若不是有限数或为负数，返回结构化拒绝 `{ allowed: 0, reason: "invalid_request" }`（存在群体时带 `cohortId`），不修改任何状态，也从不抛错；`requested = 0` 仍是合法的空操作。（2）`refill()` 自我修复：非有限的 `bucketTokens` 重置为 burst，且每次补充后令牌都被钳制在 [0, burst] 内。（3）`clearCohort` 现在也会重置桶（令牌 = burst，补充锚点更新） - 旧的清除会让被毒化的桶继续被毒化。

**实测。** 审计工具 h5 的 H2-5 序列，在一个已被标记、符合资格且时钟固定的群体上：提供 10；NaN 被以 `{allowed: 0, reason: "invalid_request"}` 拒绝（-5 与 +/-Infinity 同样）；提供 10；提供 10。快照读出 `bucketTokens = 130`（150 - 10 - 10，没有泄漏一滴）。`clearCohort` 后桶读出满值 150。补丁前在同一工具上：NaN 返回 `allowed: null`，此后每次调用都返回 `null` - 桶永不恢复。

## 3. 从不重置、从不停止增长的状态

### F-10：带 LRU 淘汰的身份状态上限

**缺陷。** 该 tripwire 把每个身份的状态（分数、结对节流条目、谓词环）保存在只增不减的映射中。长时间运行、观察大量身份的进程，运行越久每个事件的开销越大，没有上限，也没有清理。

**修复。** 该模块新增选项 `maxIdentities`（默认 2000，最小 10），沿用群体检测器已发布的模式。`identityState()` 在每次命中时刷新身份的 LRU 位置；在上限处创建状态时，通过 `removeIdentity` 淘汰最近最少活跃的身份：受害者的单例状态、结对节流条目与谓词环被移除，受害者被从其群体中拉出（`members`、`contributions`）；如果受害者是 union-find 的根，另一个成员会被提升，群体被重新键控且 `cohort.id` 被重新计算（与 `mergeIdentities` 使用的同一套手法）；被掏空的群体会被删除。宿主已声明群体的成员最后被淘汰 - 宿主是特意点名他们的。两个结对节流映射现在携带 `{ size, atMs }` 值：超过 `formationWindowMs` 的条目被视为不存在并在读取时删除（TTL），且每个映射都有 `max(1024, maxIdentities x 4)` 的大小后备上限，按插入顺序从最旧的开始修剪。`CampaignSnapshot` 新增附加字段 `stateSizes: { identities, cohorts, pairThrottles }`，以便运营者能看到上限在起作用。

**实测。** 在上限为 10 时，一个活跃的双人切片群体在 30 个单例的 churn 中存活下来，两个成员完好无损，且在 32 个不同身份之后 `stateSizes.identities` 读为 10。淘汰安静的群体成员 - 包括触发提升与重新键控的 union-find 根 - 之后留下的仍是一个可工作的引擎：不抛错，没有幽灵群体，且被淘汰的结对之后还能重新形成。一个如实说明的细节：结对节流 TTL 意味着一个结对在其窗口过后即使没有 `recheckGrowth` 也可能被重新评估；合并决定仍受每个形成标准的把关，因此这增加的是计算开销，绝不是更宽松的标准。

### F-11：周期轮换现在重置分数与贡献

**缺陷。** 当一个群体的证据周期轮换时，其累积的 CUSUM 分数与每个成员的贡献会留下来。新周期的第一个事件会立即凭借陈旧证据重新越界，再次标记该群体，并把后果对准上一周期的贡献者。

**修复。** 轮换块现在设置 `cohort.score = 0`，清除 `cohort.contributions`，并取消 `flagNotificationPending` - 一个周期就是一个证据窗口，正如接口自己的文档字符串所说。并集覆盖与已提供计数有意不重置：覆盖是真实事件，后果下限要读它。单例分数在该发现的范围之外（单例不带标记也不带后果），保持不变。

**实测。** 审计的 h6 对照：一个在 ts=1,000,000 越界的群体（account:b 在其贡献成员之中，分数达到或超过边界）在 +90 天的第一个事件时看到：`crossed: false`、`score: 0`、快照的贡献成员中没有 account:b、`consequenceTargets(...).targets = []` - 以及 `unionRecords = 165`（160 + 5 条新的），覆盖得以保留。h5 对照的读数相同：+90 天后 `flagged: false`。补丁前，两个对照都会凭借轮换后残留的分数立即重新越界。

## 4. 附加的契约变更

本波的一切都是附加性的；没有现有的签名、原因或默认值改变含义。

- **存储契约（quota-guard）：** 一个可选操作 `recordIfBelow(key, now, windowMs, limit)`，返回 `{ recorded, refusal?: "capacity", count, oldest? }`。实现它的存储获得原子执行；没有实现的存储保持补丁前的行为不变。
- **新的拒绝原因：** `unknown_action`（action-budget：该操作没有价格且未配置兜底价）与 `invalid_request`（cusum-tripwire 的 `checkServe`：请求的数量不是有限的非负数）。原子配额路径还会为存储的容量拒绝呈现 `store_capacity_exceeded`。
- **新选项：** `unknownActionCost`（action-budget 的兜底价格）、`unpricedBodyFloorUnits`（export-guard 在没有估算时的统一收费；默认 1）、`maxIdentities`（cusum-tripwire 的状态上限；默认 2000，最小 10）。
- **新的信息字段：** 每个 `QuotaCheckResult` 上以及守卫本身上的 `atomicEnforcement`；通过兜底价收费的 action-budget 结果上的 `unpriced: true`；`CampaignSnapshot` 上的 `stateSizes: { identities, cohorts, pairThrottles }`。
- **文档：** `docs/LIMITATIONS.md` 新增四行，与新行为对应（配额执行模式、导出的预留权衡、CUSUM 状态上限与标记送达、action-budget 的未知操作）。

## 6. 剩余限制与本补丁不改变的内容

- **旧式存储保持旧式行为。** 没有 `recordIfBelow` 的宿主存储仍然会和以前一样接受 F-02 的竞态 - 改变在于守卫现在会声明这一点（`atomicEnforcement: false`），而不是暗示一种硬性保证。审计自己的 V5 工具出于这一原因仍然报告 12/12：它那个延迟包装存储只实现了 peek/record，正是旧式存储这一类。审计报告第 8 节的标准（延迟存储 + 12 个并行请求 → 恰好放行 5 个）是在带原子操作的延迟存储上达成的；增加该操作加上诚实标志正是审计本身提出的最小修复形态，而不是被绕开的标准。原子性也是按每个维度/键而言的：如果后面的维度拒绝，前面维度已记录的命中会保留下来，与旧语义完全相同；多键事务不在范围内。
- **没有实测过真实的分布式存储。** `recordIfBelow` 已在自带内存存储和一个延迟包装模型上验证。本环境中不存在 Redis 或 SQL 后端；契约把原子性义务放在宿主实现身上。
- **F-16（LOW）未打补丁。** `observe()` 仍然不验证事件输入。来自审计工具的具体症状：一个时间戳为 NaN 的事件永远不会让其周期轮换（与 NaN 的每个比较都为 false），因此 h5/h6 的 ts-NaN 变体保持补丁前的行为。该变体先前已被审计的验证者否决为独立发现 - 它属于输入验证领域，在能诚实修复之前需要一个契约决定（静默的、有计数的丢弃，还是刻意的抛错）。它已排入下一波。
- **审计队列的其余部分保持原样。** 13 个 LOW 与 4 个 needs_validation 发现未被本波触及。第 2 波修复报告点名了下一波最便宜、最安全的候选（F-20、F-12、F-16、F-15），以及不应仓促处理者（F-13、F-14、F-17、F-18、F-19、F-21、F-22、F-23、F-24）。
- **修复报告如实记载的逐项残余：** 从不结算响应的导出处理程序会把其 F-03 预留保留到预算窗口滚动为止，且没有 write/end/json 表面的响应对象没有结算点；超过约 1M 个字符的 JSON 导出正文按设计收取 F-04 统一价；`checkServe` 不是 F-08 标记的重试点，且再也不被触及的群体会一直保留其待送达通知（按设计，没有计时器）；当每个身份都是已声明成员时淘汰已声明群体成员的 F-10 兜底路径没有专门的测试，且结对节流 TTL 在大轨迹上的性能未测量；F-11 让单例分数不随周期轮换，在该发现的范围之外。
- **一个工具缺陷属于审计，而非 SDK：** 审计的 h5.cjs 在其第 76 行崩溃（读取一个为 null 的原始存储的 `.subjects`，H1-5 块），在补丁前与已打补丁的 dist 上完全相同，且发生在本波触及的所有项目都已打印完毕之后。它被保持原样。
