# v2.6.1 深入解析

## 摘要

v2.6.1 是一个补丁版本，只包含三处修复，全部来自对已发布的 v2.6.0 代码树的全面安全审计（39 个候选项经过对抗性核验 → 24 个确认的发现；获批的修复范围是唯一的 HIGH 级发现加上"杀死宿主"组 F-06/F-07）。没有新功能，也没有破坏性变更：对公共契约的影响仅是新增性的（一个新拒绝原因、一个此前只以死代码形式存在的拒绝类型，以及可选的诊断字段）。测试套件：305 个测试（303 个通过，0 个失败，2 个原有的 RSA-PSS 跳过），较 v2.6.0 的 298 个有所增加，并新增 7 个回归测试。其余审计发现均未触及，仍在队列中。

## 1. F-01 - 跨主体的幂等重放（HIGH）

### v2.6.0 中的漏洞

两个账本都接受一个 `idempotencyKey`，以便宿主可以安全地重试一次预留：用同一 key 的第二次调用会以 `duplicate: true` 返回原始预留，而不是重复预留。在 v2.6.0 中，重复分支只以幂等键为查找依据 - 它从不检查提问者是谁、请求的是什么。任何获知或猜中另一主体 key 的调用方，都可以用任意记录 id（公开账本）或不同的主体/操作/成本（操作预算）重放该 key，并针对原始主体的预留获得 `allowed: true, duplicate: true`：陌生人的提取被记在受害者的预留上，而该预留所守住的群体上限也可以被借道突破。修复前审计测试框架的结论是：`replayAllowed: true, duplicate: true, sameReservation: true`，且提交后的并集包含陌生人的 4 个 id。

### 修复

现在，重放必须与该 key 最初创建的预留相匹配，检查点位于最后的信任决策点：reserve 的重复分支，且处于同一个存储事务内，因此该检查无法被竞态绕过。

- **公开账本**（`src/tier2-active/disclosure-ledger.ts`）：每个预留现在存储一个 `idemFingerprint` - 对主体 + long 标志 + 仅计数金额 + 排序后的记录 id 计算的 64 位 FNV-1a 哈希。只有当已存储的主体与已存储的指纹都与传入请求匹配时，重复分支才返回该重复项。
- **操作预算**（`src/tier2-active/action-budget.ts`）：预留本身已经存储了主体/操作/成本/群体 id，因此重复分支直接比较这四个字段（`samePayload`）；无需新增任何存储状态。
- 任何不匹配都会以新的原因 `idempotency_conflict` 拒绝（两个模块的原因联合类型都已扩展）。两个模块中 `idempotencyKey` 的文档注释以及 `docs/LIMITATIONS.md` 现在都明确陈述了契约：key 必须由宿主生成且不可猜测 - 被猜中的 key 也不再能搭乘另一个主体的预留。

### 兼容性说明

由 v2.6.0 或更早代码持久化的预留不携带指纹。与其在未经验证的情况下予以承认（旧的、可被利用的行为），现在针对它的重放会在该预留剩余的 TTL 内失败关闭，返回 `idempotency_conflict` - 默认 2 分钟，长预留路径上最长 15 分钟。新的预留不受影响，精确重放（同一主体、同一载荷）仍返回 `duplicate: true`。

## 2. F-06 - 存储失败时失败关闭，而不是抛异常

### v2.6.0 中的漏洞

账本通过宿主提供的存储来持久化状态。在 v2.6.0 中，损坏或故障的存储会把原始异常抛出 SDK 的公共方法：被截断的 JSON 状态抛出 `SyntaxError: Unterminated string in JSON`，形态错误的状态抛出 `TypeError: Cannot convert undefined or null to object`，CAS 耗尽则抛出普通的 `Error`。审计用朴素的宿主接线方式（SDK 周围没有 try/catch，就是 README 最简示例的接线方式）做的实机测试清楚地展示了后果：在存储已死的情况下，宿主进程在第一个请求时就崩溃了（未处理的 rejection）。防滥用层中的存储问题，绝不能演变成宿主的可用性问题。

### 修复

存储损坏与故障在每个模块的边界被转换为结构化的拒绝，因此任何存储异常都无法逃逸到宿主的请求处理中：

- **公开账本：** 新增 `LedgerStoreError` 类型；已存储的状态在读取时被解析并做形态验证（`parseStoredState`、`isValidLedgerState` - 核心字段、桶数值、证据与幂等形态、注册表，以及每一个已存储的位图都必须能解码）。当事务的更新函数看到无效形态时，变更会中止且不写入；CAS 耗尽在内部抛出 `LedgerStoreError`，并由每个公共方法转换：`reserveDisclosure` 以原因 `store_conflict` 拒绝（该原因在 v2.6.0 的类型联合中存在，但属于死代码 - 从未被返回过），`commitReservation` 返回 `{committed: false, reason: "store_conflict"}`，release/sweep/recordEvidence/declareRegistry 返回携带 `reason: "store_conflict"` 的结果，`snapshot` / `checkRegistryCompleteness` 则返回空状态后备快照加上一个 `storeError: "store_conflict"` 字段。
- **操作预算：** 在已有的 `StoreConflictError`（从未被抛出）旁边新增 `StoreDataError`；`isValidActionBudgetState` + `parseActionBudgetState` 在读取时验证；变更路径包裹事务抛出的异常和审计路径 put 抛出的异常，并在形态无效时中止；commit/release/sweep/declare/pacing/clear/snapshot 都通过 `isStoreFailure` 辅助函数返回 `store_conflict` 拒绝。
- **配额守卫**（`src/tier2-active/quota-guard.ts`）：新增拒绝类型 `store_unavailable`。peek 循环验证返回的快照（一个带有有限数值 `count` 的对象）并捕获存储抛出的异常，记录循环同样捕获 - `checkRequest` 现在回答一个结构化的 429 决定，而不是传播存储的异常。

### 实机复测

在打补丁的构建上，用审计自己的测试框架和实机宿主重新运行：被截断的 JSON 和形态错误的 JSON 都返回 `{"allowed": false, "reason": "store_conflict"}`，不再抛异常。朴素接线的实机宿主在存储已死时，以 HTTP 429 回答了两个请求，且进程保持存活（修复前：在第一个请求就崩溃）。一个接线正确的受保护宿主，在被强制制造存储故障时，从 HTTP 500（此前它只能靠自己的 try/catch 才幸存）变为结构化的 HTTP 429 `store_unavailable`（"Quota store unavailable; the request was rejected rather than admitted unaccounted."）。在健康的存储上，合法请求以约 1-8 毫秒返回 200 ×3 - 没有回归。失败模式对准入决定刻意采用失败关闭：SDK 无法记账的请求会被拒绝，绝不会在未记账的情况下被放行。

## 3. F-07 - 用于记录并集的稀疏分块位图

### v2.6.0 中的漏洞

公开账本用一个稠密位图跟踪已服务记录 id 的精确并集：每个 id 一个比特，大小由见过的最大 id 决定。因此内存与序列化成本随最大 id 的值增长，而不是随记录数量增长。使用雪花规模或 int64 id 的数据集 - 无需任何攻击者 - 在正常运行中就会撞上这个问题：预留一条 id 为 10^8 的记录需要 1,439 毫秒，并产生 16,670,239 字节的序列化状态；预留 id 2^53-1 则把 `RangeError: Array buffer allocation failed` 直接抛出 `reserveDisclosure` 之外。

### 修复

稠密位图在 `disclosure-ledger.ts` 中被替换为**稀疏分块位图**：一个在 8192 比特块之上的 `Map<chunkIndex, Uint8Array(1024)>`。状态与工作量现在随不同记录的数量增长，永远不随 id 值增长。线格式为 `"s1." + base64url([uint32LE chunkIndex | chunk bytes]*)`。所有位图辅助函数（`bitmapFromBase64`、`bitmapToBase64`、`bitmapHas`、`bitmapWithIds`、`bitmapUnion`、`bitmapPopcount`、`bitmapNewIds`）都已在分块类型上重写。极端 id 不会被拒绝，也不会有任何 id 能抛出异常：每个 id 的成本恰好是一个 1024 字节的块，被精确地服务与计量 - 这就为恰好撞上此 bug 的雪花/int64 id 数据群体保留了账本的精确性契约。

### 旧状态兼容性

由 v2.6.0 或更早代码持久化的状态（稠密格式）仍然可以解码：稠密字节在读取时被转换为块，已持久化的账本继续工作，并在下一次写入时以稀疏 `s1.` 格式重写。一个手工构造的稠密状态，并集字节 0b00001010（id {1, 3}），加载后 `committedRecords` = 2，再次交付这些 id 是免费的，而新 id 恰好收费一次。形态错误的稀疏载荷会抛出 `LedgerStoreError`，并通过 F-06 的管道表现为 `store_conflict`，而不是静默解码成一个空位图（那样会悄悄清零上限的记忆）。

## 4. 复测数字

下面每个数字都来自审计测试框架在打补丁的构建上原封不动的重新运行，外加软件包测试套件：

- **F-01：** 陌生人重放（账本）- `replayAllowed: true` → `replayAllowed: false`；提交后的并集只包含原始主体的 4 个 id。跨主体/操作重放（预算）- `replayAllowed: true, replayCost: 10` → `replayAllowed: false`。
- **F-06：** 被截断的 JSON - 抛出 `SyntaxError` → `{"allowed": false, "reason": "store_conflict"}`；形态错误的 JSON - 抛出 `TypeError` → 同样的结构化拒绝。朴素接线的实机宿主 + 死存储 - 在第一个请求崩溃 → 两个 HTTP 429 回答，进程存活。受保护实机宿主 + 强制存储故障 - HTTP 500 → 结构化的 HTTP 429 `store_unavailable`。健康的存储：合法请求 200 ×3，约 1-8 毫秒。
- **F-07：** 预留单个 id 10^8 - 1,439 毫秒 / 16,670,239 字节 → **3 毫秒 / 1,745 字节**。预留 id 2^53-1 - 逃逸的 `RangeError` → `allowed: true`，结构化的预留，不抛异常。
- **测试套件：** `npm run check` - 298 个测试（296 个通过） → **305 个测试（303 个通过，0 个失败，2 个 RSA-PSS 跳过）**，增量为 7 个新的回归测试：两个账本上的重放拒绝矩阵、两个账本加上配额守卫的损坏/死亡存储矩阵、极端 id 成本边界，以及旧稠密状态兼容性。`npm run benchmark:build-sdk` 通过。

## 5. 此补丁不改变的内容

- **对行为良好的宿主没有行为变化：** 价格、预算、上限、节奏、群体规则、校准默认值以及每一个已发布的常量都与 v2.6.0 完全一致。存储健康且自行生成幂等键的宿主不会看到任何差异，除了那些此前会抛异常、或静默地替错误主体成功的拒绝路径。
- **其余审计发现未在此修复：** F-02、F-03、F-04、F-05、F-08 以及 24 个确认发现中的其余部分，保持其 v2.6.0 的行为（测试框架的重新运行确认，例如，未定价的操作仍然会被授予，平行配额检查的行为与先前相同）。它们排在后续轮次的队列中；此补丁刻意不触及它们。
- **不夸大声明：** 审计的结论保持原样 - 这三处修复中的任何一处都不改变 README 中任何实测结果数字，`docs/LIMITATIONS.md` 中已知的局限其余保持不变（该文件增加了上文所述的幂等键契约说明）。
