# antiRea v2.9.0 深入解析

> 一个由外向内构建的 minor 版本：一次对 51 个有来源的真实数据泄露案例的收割，与 SDK 对照之后发现，最大的真实缺口在字段层面。以下全部内容都是案例记录、实验室记录和套件记录--语料是带种子的合成数据，这里的任何数字都不是真实流量测量。

## 第 1 部分：发布了什么

一个新模块 `createSurfaceGuard`，和一个成文的模式：已声明 cohort 的联合预算（`examples/declared-cohort-budget`）。一切都是新增；没有任何现有模块改变行为。套件：830 个测试（828 通过、0 失败、2 个预先存在的 RSA-PSS 跳过），高于 2.8.1 的 817 个--新增 13 个测试，零个既有期望被修改。本版本通过了强制性的 range 发布门 6/6（SDK 套件、冻结的 FP/检测单元格、range 实时冒烟）。

## 第 2 部分：问题--负载本身

2026-11-13 的收割收集了 12 个根因类别中的 51 个有来源事件。其中三类本就是这个 SDK 的主场（搜索/列表枚举、导出范围、合法 API 爬取）。完全没有覆盖的那一类是最简单的一类：**一个响应携带了路由从未打算发布的字段**。Spoutible 的个人资料 API 对任意用户名返回 bcrypt 密码哈希、2FA 密钥和密码重置码。eHUST 的学生搜索端点在搜索结果中返回密码哈希、身份证号、保险号和银行账号。Microsoft Power Apps 的默认 OData 共享以同样的方式暴露了 3,800 万条记录。没有任何预算能抓住这一点：泄露点不是一个身份拿走了多少，而是一个普通响应里装了什么。入站方向的镜像失败是批量赋值：写入处理器仅仅因为调用方提交了 `role`、`is_superuser` 或 `owner_id` 就把它们绑定（GitHub 2012、Rocket.Chat、Langflow）。

## 第 3 部分：机制--两层、双向

`createSurfaceGuard` 在 JSON 形态的负载越界之前检查它们：

- **Denylist 层（零配置）：** 字段名先被规范化（小写、去掉 `_`/`-`/空格--`password_hash`、`passwordHash` 与 `Password-Hash` 是同一个字段），再与响应侧的内置敏感模式（凭证材料、secret、token、身份证号、银行/保险号）和请求侧的特权模式（role、admin 标志、所有权 id）对照。仅这一层就能抓住无人声明过的路由上的过宽响应。
- **Schema 层（主机声明）：** 按路由声明的字段名 allowlist。allowlist 之外的任何字段都是 `undeclared` 违规。主机确实声明过的字段豁免于 denylist 层--声明是主机自己的刻意行为（登录响应合法地返回 token）。
- **后果遵循分级法则：** 默认模式是 `advisory`--违规通过 `onViolation` 报告，负载从不被触碰。`strip` 返回一份已净化的深拷贝；`block` 把结果标记为不通过。守卫从不自行升级自己的模式。
- **成本有界：** 遍历是迭代式的，带节点上限（默认 10,000）；超过上限时，结果携带 `truncated: true`，而不是永远扫描一个敌意负载。

## 第 4 部分：测量（预注册门 SG-G1..SG-G6，种子 20297xxx）

- SG-G1：一个 eHUST 形态的 fixture 精确标记 password、password2、idNumber、insuranceNumber 和 bankAccount，全部为 `sensitive`。
- SG-G2：2,000 个符合 schema 的合法响应--**0 误报**。
- SG-G3：500 个过宽响应，注入 1,194 个取自真实案例字段清单的敏感字段，在无 schema（仅 denylist）下检查--**捕获 1,194 / 1,194**。
- SG-G4：2,000 个合法请求--**0 误报**；500 次写入注入 918 个特权字段--**捕获 918 / 918**。
- SG-G5：一个 100,000 字段的敌意负载被上限截断（`truncated`），实验室 VM 中位数 36 ms。
- SG-G6：完整套件加 range 发布门，6/6 PASS。

如实记录：SG-G2 的第一次运行报告了 1,003 个误报--错误在实验室自己的语料生成器，它生成了已声明 schema 中不存在的嵌套字段；守卫是对的。生成器被修正为与它的 schema 一致，各道门原样重跑。

## 第 5 部分：已声明 cohort 模式

本版本的后半部分刻意只是文档。项目 range 上真实的 REA 6.9.0 测试（2026-11-12）显示：一个 4 身份 herd 在约 15 秒内掏空了 500 条记录的数据集，而所有 herd 信号保持沉默--按身份的预算在轮换下被稀释。应对方案的 B 步在 range 上建立了常驻的参考人群，并证明让小突发无法被评分的是 cohort 的事件下限，而不是缺少参考数据；A 步原型化了合法的硬答案：**一个以主机声明的 cohort id 为键的 `createRecordBudget`**，使该 cohort 的不同记录并集被精确封顶。在真实 HTTP 上测量：已声明的 herd 恰好停在 500 中的 150（7 次 cohort 层拒绝、0 次身份层拒绝），完全相同的未声明 herd 拿走了 500 / 500，只有一个成员的已声明 cohort 从未在它自己的 150 之前被拒绝。

它以模式而非 API 的形式发布，原因有二：包装器不会在已发布原语之上增加任何能力--只会多一个要维护的名字；而且捆绑的存储是单进程的，有名字的导出会诱使横向扩展的主机把这个模式误认为生产上限（那条路已经以 disclosure ledger 的 `reserveDisclosure` 和 tripwire 的已声明 campaign 上限的形式发布）。主机缺的是接线知识，而这正是 `examples/declared-cohort-budget` 提供的：README、可复制改编的接线代码，以及对这三个数字的独立验证。

## 第 6 部分：声明的限制

- 守卫读的是字段名，不是值，也不是所有权。一个已声明字段装着另一个用户的数据时仍会通过--BOLA 仍然是主机的授权逻辑，正如 LIMITATIONS 一直所说。
- 藏在一个无害的未声明名字之下的敏感值会逃过 denylist 层；schema 层在已声明路由上仍能抓住它。
- Denylist 是在合成语料和真实案例字段清单上校准的，不是在任何主机的生产流量上；不寻常但合法的词汇（返回 `balance` 的金融 API）通过声明 schema 来处理。
- 联合预算模式按设计由声明开启：主机从未声明的轮换只保留其按身份的预算，而被声明进同一个 cohort 的合法团队将共享它的上限--这个误报由主机自己的声明造成，并且被写进文档，而不是被隐藏。
